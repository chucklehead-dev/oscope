Design proposal · measured spike · 23 Sep 2026

oscope-core: a Rust engine under oscope

A local ClickStack and Langfuse on chDB, built as one Rust library with a C ABI. It serves four ways: an in-process recorder any language can embed, a single-binary collector with API and web UI, a terminal UI, and a Jolt binding so samizdat and naval-battle keep working unchanged.

Builds on: oscope, jolt-chdb, jolt-otel-clickhousechDB 26.7.3Spike: 2.6k lines of Rust, C and Python

01The short answer

Your perf problem is not chDB. jolt-chdb's own probe measured a 10.3 ms direct native insert for the same 512-row statement that takes 60–2,600 ms through the Jolt paths. The time goes to managed JSON encoding, SQL string building, placeholder scanning, JSON WAL records and GC on the Chez heap. So the fix is to move the hot path, the encoders and the WAL out of the managed heap. Replacing chDB would not help.

58 nsper span on the recording thread (one-shot API), with zero allocations
66krows/s at 512-row batches on disk with a per-batch fsync WAL (your target: 25k)
204krows/s at 10k-row batches with RowBinary streaming insert
184krows/s WAL recovery into a fresh process (Jolt today: ~17k)
Recommend

Write the engine in Rust as oscope-core: recorder, assembler, RowBinary encoders, WAL, chDB writer, OTLP decoder and query service. Expose it as a C ABI (cdylib plus staticlib). Keep Jolt as a host language and as the place UI and policy experiments can live.

Keep

ClickStack table shapes, oscope's closed-allowlist query plans, the Durable V1 protocol, and the GenAI attribute manifest from samizdat. These are good decisions. Only the runtime underneath them changes.

Change

Stop sending JSONEachRow SQL text across FFI. Stream RowBinary through chdb_stream_insert, WAL the encoded bytes, coalesce small batches, and run the upstream chdb-rust Durable implementation instead of maintaining a port.

Watch

libchdb is 566 MB. "Single binary" in practice means one executable plus one engine file, or a self-extracting bundle. See Risks.

03What the spike measured

I built the proposed hot path, drain, encoder, writer, WAL and OTLP decoder in Rust against libchdb 26.7.3 and measured each stage. The machine was a 4 vCPU Xeon @ 2.10 GHz VM with 15 GB RAM. What the numbers say about the design

  • Each insert has a fixed cost of about 7 ms. Most of it is MergeTree creating a part. It makes JSONEachRow and RowBinary tie at 512 rows. At 10k rows, RowBinary is 1.85× faster and half the bytes (274 vs 536 B/row). So batch size matters more than format, and a Buffer table cuts that fixed cost to about 2.5 ms for apps that flush often.
  • Encoding is not the bottleneck in Rust. RowBinary encoding is under 3% of batch time. The drain thread assembles and encodes a row in about 0.5 µs, so one core can drain about 1.8 M rows/s. chDB inserts are the ceiling at about 200k rows/s per writer.
  • The durable WAL is almost free. Writing already-encoded RowBinary bytes with a CRC frame and fsyncing each batch costs 1–2 ms per 10k rows. The Jolt design pays for JSON-encoding every statement a second time.
  • Clock reads are a real share of the hot path. clock_gettime costs 28 ns on this VM and the incremental API calls it twice per span. A TSC-based clock calibrated by the drain thread would bring the hot path to about 60 ns.
Found along the way. Putting binary data inline after FORMAT RowBinary\n in chdb_query_n fails intermittently. The parser skips leading whitespace, so a batch whose first timestamp byte is 0x09, 0x0A, 0x0D or 0x20 misaligns. That happens about 4 times in 256 batches. Always use chdb_stream_insert. The ThreadStatus corruption jolt-chdb reports for long-running stream inserts did not reproduce here: several hundred stream inserts per process on one dedicated writer thread, with no errors.

04Architecture

There is one core and four ways to run it. Every path into storage converges on the same writer, so in-process recording, the OTLP collector and WAL replay share batching, durability and schema.

05The C ABI

The rules are the ones that make an ABI cheap from every FFI: integer handles, borrowed (ptr, len) strings, plain structs, no callbacks, and no ownership transfer on the recording path. Strings you repeat, such as span names and attribute keys, are interned once at setup, so hot calls pass a u32. Parent context comes from a thread-local span stack, and an explicit parent can be passed instead. When a ring is full, the recorder refuses the whole span at START and counts it. It never blocks the caller.

/* incremental: natural for C/Rust/Zig and for wrappers that map to with-span */
uint64_t osc_span_start(uint32_t name, uint8_t kind);            // parent = innermost open span
void     osc_span_attr_i64(uint64_t span, uint32_t key, int64_t v);
void     osc_span_attr_str(uint64_t span, uint32_t key, osc_str v);
void     osc_span_end(uint64_t span, uint8_t status);

/* one-shot: one crossing per finished span, for hosts where FFI calls cost more */
int32_t  osc_span_record(const osc_span_rec *rec);                // ids, times, attrs[]
int32_t  osc_log(uint8_t severity, osc_str body, const osc_attr *attrs, uint32_t n);

/* proposed, not in the spike: the host writes N records in the ring wire format
   into its own buffer and hands them over in one call (zero per-span crossings) */
int32_t  osc_submit(const uint8_t *records, size_t len);

/* lifecycle and read side */
int32_t  osc_start(const osc_config *);   int32_t osc_flush(uint32_t timeout_ms);
int32_t  osc_query(osc_str sql, const char *fmt, uint8_t **out, size_t *len);  void osc_free(uint8_t*, size_t);

The spike checked three of these paths end to end. A C program linked against the library recorded nested spans from two threads plus correlated logs, and it read them back through osc_query. A C program that loads the library with dlopen, as every FFI does, did the same. Python ctypes recorded 200,000 spans with exact counts and no drops.

06Storage and schema

  • ClickStack tables, unchanged. otel_traces, otel_logs and otel_metrics_{gauge,sum,histogram} keep the collector's column names and types, including the Events and Links nested columns. HyperDX or ClickStack pointed at an exported database should just work.
  • RowBinary streaming insert is the only write path. Encoders append into reused buffers. The writer holds one connection, reads go through a second connection to the same path, and the two never contend.
  • Batching policy lives in config, not code. Flush at N rows or T ms, whichever comes first. Use a Buffer engine table when an embedded app wants data visible within a few ms. Default to 8–10k-row inserts for throughput.
  • Langfuse-shaped views come from GenAI conventions. A materialised view over otel_traces fills llm_generations from gen_ai.* and langfuse.* attributes: model, input, output and total tokens, cache hits, latency and cost. Cost comes from a price table kept in SQLite. samizdat's attribute manifest already emits these attributes. Scores and feedback go in an llm_scores MergeTree table keyed by trace and observation id.
  • SQLite plays the role Mongo plays in HyperDX. It holds sources, saved searches, dashboards, alert rules, the model price table, prompt versions, dataset definitions and annotation queues. This is small and relational, needs transactions, and changes by hand. SQLite in WAL mode fits and adds only about 1 MB.
  • Typed attribute promotion stays. oscope's promoted typed columns become ALTER TABLE ... ADD COLUMN ... MATERIALIZED SpanAttributes['k'] driven by the same manifest. The hot path is unaffected.

07Durability modes

ModeStorageAck meansCrash loses
Ephemeral:memory:enqueuedeverything
LocalchDB pathinserted as a partthe unflushed batch plus parts not yet fsynced (chDB does not fsync parts by default)
Local durablepath + binary WALWAL frame fsynced (group commit)nothing acknowledged
Object-store durableDurable V1 through chdb-rust (features = ["durable"])WAL segment published by head.json CASnothing acknowledged. Single-writer lease with generation fencing, as today.

The WAL frame is magic · table · rows · len · crc32 · RowBinary payload. Replay needs no parsing: it streams the payload straight back into chdb_stream_insert. That is why recovery runs at 184k rows/s against about 17k in Jolt. For exactly-once replay, each frame gets a sequence number used as insert_deduplication_token, with non_replicated_deduplication_window enabled on the tables. The spike truncates the WAL after replay and does not have this yet.

For the object-store tier, jolt-chdb/bench/rust-durable-recovery-oracle already depends on chdb-rust with its durable feature, the implementation your Jolt code is qualified against. A Rust core can use it directly. Your Quint models and ITF traces stay valuable as conformance tests run against that library.

08Collector

  • now OTLP/HTTP JSON on /v1/traces|logs|metrics. The spike's borrowing serde decoder writes RowBinary directly with no intermediate row objects. Decode runs per request on the HTTP worker threads and scales with cores. The single writer coalesces requests into large inserts. Coalescing took ingest from 44k to 138k spans/s.
  • next OTLP/HTTP protobuf and gzip. This is prost plus the opentelemetry-proto definitions: the same decode-to-RowBinary shape and less work than JSON. It is days of work, not a project.
  • later OTLP/gRPC with tonic on :4317, behind a cargo feature to keep the default binary small.
  • Admission control keeps oscope's semantics. The body cap and bounded queue stay; a full queue returns 429 and a failed durability boundary returns 503. In durable mode, 2xx waits for the WAL group commit, not the chDB insert. Group commit batches concurrent requests into one fsync.
  • Receiver and embedded recording share the writer. An app can embed libosc and also accept OTLP from child processes, such as samizdat's tool subprocesses using TRACEPARENT, into one store.

09UI: HyperDX-lite and Langfuse-lite

The UI talks only to the HTTP API. The same API serves the web UI, the TUI and embedded viewers. Queries are oscope's typed, closed-allowlist plans compiled to SQL with bound parameters (chdb_query_with_params), so no user text ever becomes an identifier or expression.

HyperDX-lite

  • Search bar with a Lucene-style subset (service:checkout level:error http.status_code:>=500) compiled to plans
  • Log and span tables with a live tail over SSE, plus a histogram of volume by severity
  • Trace waterfall with correlated logs inline, via otel_traces_trace_id_ts
  • Service view showing RED metrics from spans: rate, errors, p50/p95/p99
  • Metric explorer for gauge, sum and histogram, covering your existing explorers
  • Saved searches and dashboards stored in SQLite
  • Export to Arrow or Parquet, as oscope's raw_export does today

Langfuse-lite

  • Sessions → traces → observations tree using langfuse.session.id and langfuse.observation.type
  • Generations table: model, tokens, cost, latency, finish reason
  • Input and output viewer, which shows digest-only content when capture is off (samizdat's default)
  • Scores and feedback: record from the UI or the API, and aggregate per model and prompt version
  • Cost and token dashboards over time and per model
  • Later: prompt registry, datasets and evaluation runs, all metadata in SQLite

Web tech. Use a server-driven page with a small interactive layer: htmx or a Preact bundle of about 30 KB, with uPlot for charts. Compile it into the binary with rust-embed. The waterfall and the table grid are the only parts that need real client code. Everything else can be server-rendered, as oscope's Ring UI is today, and it still works without JavaScript.

10Alternatives

OptionVerdictReasoning
Rust core + C ABIRecommendedMeasured above. It gives the best C ABI story of any safe language (cbindgen, cdylib and staticlib), mature crates for everything in this design (axum, prost, tonic, ratatui, rusqlite), and chdb-rust already includes Durable.
Zig coreViableIt is just as good at C interop and at controlling allocation. The ecosystem for HTTP, protobuf and TUI is thinner, and there is no Durable library, so you would port it again.
C++ coreViable, not preferredIt is closest to chDB internals and could link the static engine one day. It costs more in memory safety for code that parses untrusted network input.
GoCollector onlyIt works well as a standalone collector. It is a poor in-process library for other languages: cgo cost, its own runtime and GC in the host, and an awkward c-shared build.
Stay in Jolt, tweakedPossible for the 25k targetThe spike suggests four changes would meet 25k rows/s at 512 rows even with managed code. (1) Encode RowBinary into reused bytevectors instead of JSON strings. (2) Send it with chdb_stream_insert, so there is no SQL text and no placeholder scan. (3) WAL the same bytes. (4) Coalesce into 8–10k-row batches. That removes every step in your probe that costs over 500 ms. It does not give you a cross-language ABI.

These paths can be combined. A good sequence is to build the Rust core and point jolt-otel-clickhouse at it through jolt-oscope. Your Jolt code keeps its APIs and loses its hot path.

11Risks and open questions

  • Binary size. libchdb.so is 566 MB already stripped (174 MB as a tarball). The Rust core is 5.8 MB. Options: ship a two-file distribution, or a self-extracting single executable that unpacks the engine to a cache directory on first run. Another option is the jolt-chdb approach of a pinned, digest-checked download. A statically linked engine would need an upstream chDB build.
  • The engine is process-global. chDB allows one storage path per process, and closing the last connection shuts the engine down; reconnecting is risky on macOS. If the host app already uses chDB, the embedded recorder has to share its engine and path. The API should take an existing connection.
  • Load order. When libchdb was a transitive startup dependency behind libc, its static initialisers recursed and the process crashed before main. The fix was either linking -lchdb first or loading with dlopen. Bindings should dlopen. Document the link order for static hosts.
  • Signal handlers. chDB installs handlers. Embedded hosts such as game loops should call chdb_set_signal_handlers_enabled(0) before connecting. This needs a test in naval-battle.
  • Stream insert stability. It did not reproduce here, but jolt-chdb saw ThreadStatus corruption. Keep the writer on one dedicated OS thread, as the spike does, and add a soak test of hours rather than minutes.
  • Overload semantics. Attribute records can still drop after their span's START succeeds, which leaves a partial span. Both drops are counted. If partial spans are unacceptable, reserve attribute space at START too, or mark the span truncated.
  • Spans ended on a different thread from the one that started them. The assembler holds END records that arrive before their START. Open spans need an age-based eviction, not written yet, so a span that never ends cannot grow memory without bound.

12Plan

1

Core library

Harden the spike into oscope-core: logs and metrics (histograms aggregated on the drain side), Events and Links, a TSC clock, osc_submit, cbindgen headers, and a soak test. Done when a Rust and a C embedding hold 100k spans/s for an hour with exact counts.

2

Jolt binding and adoption

Write jolt-oscope as a casselc/otel exporter over osc_submit. Switch naval-battle's woven build and samizdat's local destination to it. Done when both run with unchanged app code and the naval-battle frame budget holds.

3

Single binary and collector

Build the oscope executable: axum, OTLP/HTTP JSON and protobuf, 429/503 admission, the durable local WAL with group commit and dedup tokens, and the HTTP API. Done when oscope's existing sample emitter and Langfuse interop gate pass against it.

4

HyperDX-lite UI and TUI

Search, tables, live tail, waterfall, service view, saved searches in SQLite, and the ratatui client over the same API.

5

Langfuse-lite and Durable object store

Generation views, costs, scores, and the session tree. Durable V1 through chdb-rust, with your Quint and ITF traces as its conformance suite.
